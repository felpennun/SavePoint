# Phase 01.1: Real-Scale Catalogue and Product Experience - Context

**Gathered:** 2026-09-05, immediately after Phase 1's human sign-off (`docs/verification/phase-01-signoff.md`)
**Status:** Ready for planning (some specifics still open -- see `<open_questions>`)

<domain>
## Phase Boundary

Grow SavePoint from Phase 1's small curated 150-game demo corpus into something that reads and functions like a real product: a real-scale IGDB-sourced catalogue, a visual redesign closer to established cataloguing products, catalogue sorting/filtering, multiple working preloaded accounts, and a dedicated genre-based recommendations page. This is explicitly an author-requested, author-prioritized insertion ahead of the already-planned Phase 2 (Comparative Evaluation Protocol) -- it is not a continuation of Phase 1's three-day-demo constraints, and it does not need to fit in a single day despite the author's initial hope; the author accepted this when the scope tradeoff was made explicit.

Full recommender algorithm comparison (content-based/collaborative/hybrid, Phase 2's own scope), advanced inventory fields, comments/custom lists, and export/import (Phase 3's scope) remain out of this phase.

</domain>

<decisions>
## Implementation Decisions

### Priority order (author's own, not the default)
- **D-01:** Mass catalogue import (IGDB) and interface redesign come first.
- **D-02:** Real login system with multiple preloaded accounts comes second.
- **D-03:** Catalogue sorting/filtering and search filters come third.
- **D-04:** An independent recommendations page (by genre / user taste) comes fourth.

### Data source
- **D-05:** IGDB is the chosen data source for the real-scale catalogue, explicitly chosen over RAWG and over scaling the existing Wikidata pipeline further. This decision and its rationale (coverage, licensing/attribution terms, quotas, stability, cost -- DATA-04's own required comparison) must be documented in this phase's own ADR, since the author asked explicitly for it to be recorded for the thesis.
- **D-06:** Complete cover-image coverage across the full catalogue matters to the author, but may be delivered incrementally after the initial import -- it must not block the rest of this phase's work. A missing cover falls back to the same first-party placeholder pattern established in Phase 1 (D-07 in `01-CONTEXT.md`).

### Visual direction
- **D-07:** The redesign should read as a professional, product-grade cataloguing app -- the author named Goodreads and OpenCritic as reference points for density, typography, and imagery treatment. This is a direction, not a locked spec; the actual design contract belongs to `$gsd-ui-phase 01.1`.

### Accounts
- **D-08 (RESOLVED 2026-09-05, after research flagged a real scope conflict):** The research pass found that `REQUIREMENTS.md`'s own Out-of-Scope table explicitly excludes "Open production registration in v1" ("Initial release is a controlled academic demonstration"), and `AUTH-03` ("Visitor can register an unrestricted production account") is explicitly assigned to v2, not v1. The author was asked directly and chose a middle path: **AUTH-03 / unrestricted public production registration stays out of scope** -- this is NOT reopened. Instead, this phase builds a genuinely functional self-registration form (not just admin-seeded fixtures) so a demo visitor can create a real working account, browse the catalogue, and add games to their own collection -- but this still lives within AUTH-02's "synthetic/demo users" territory (this phase owns AUTH-02, moved from Phase 2), not as literal unrestricted public production registration. The distinction that matters: the *form and account-creation flow are real and functional*, but the deployment/scope boundary (controlled demo, not open production) is unchanged. Preloaded/admin-created accounts (plural, unlike Phase 1's single `DEMO_ACCOUNT_ANCHOR_ID`) are still wanted alongside this, per the author's original "ambas cosas" (both) answer.

### Recommendations page
- **D-09:** The new page must be visibly distinct from the existing public popularity baseline (`REC-02`/`rank_popularity_v1`) -- it reflects the signed-in user's own recorded activity/genre preferences, not an aggregate. The exact algorithm (a simple genre-preference heuristic vs. something closer to Phase 2's content-based work) is an open question -- likely a simple heuristic given Phase 2 owns the rigorous recommender comparison.

</decisions>

<open_questions>
## Open Questions for Planning/Discussion

- ~~Exact scope of "real login system"~~ RESOLVED, see D-08: functional self-registration within the still-controlled-demo boundary, AUTH-03 stays out of scope.
- Exact catalogue scale target: IGDB's full catalogue, or a large-but-bounded subset (hundreds of thousands is the author's stated ambition, not necessarily every single IGDB entry). Research estimates IGDB's real size at roughly 230K-430K entries depending on category filtering (base games vs. including ports/DLC/bundles) -- the planner should propose a concrete boundary.
- Exact filter/sort fields beyond platform and genre (release year? rating? completion status?) -- author explicitly wants "standard" fields from comparable sites, delegated to the planner/researcher's own findings.
- Exact recommendation heuristic for the new page (simple genre-frequency-from-library vs. something more sophisticated).
- **Whether IGDB's terms permit the storage/redistribution pattern already used for Wikidata/Commons covers, or require hotlinking instead** -- research could not confirm this from a primary source this session (`api-docs.igdb.com` returned 403 to every fetch attempt; the "50,000 requests/month" figure commonly cited elsewhere appears to describe a deprecated pre-Twitch API tier, not current IGDB v4 -- needs a live, authenticated probe against the real API before the import architecture is locked in). This is exactly what DATA-04's comparison must settle before import begins.
- Whether IGDB still enforces any monthly request quota under the current Twitch-OAuth2 v4 API (only the 4 req/s + 8-concurrent rate limit is confirmed with higher confidence) -- same live-probe caveat as above.

## From Research (01.1-RESEARCH.md, commit 7557e5e)

- The existing Wikidata import pattern (`import_catalogue.py`: everything in memory, one `transaction.atomic()` + one advisory lock for the whole run) does not scale to IGDB's volume -- needs batched transactions with a resumable, id-based (not offset-based) cursor.
- No `Genre` model exists anywhere in the codebase today. `CAT-02` and `REC-10` both need one; recommend adding only a minimal `Genre` entity now, not the full `CAT-05` (franchise/developer/publisher/mode/tag) scope, which stays Phase 4's.
- The Wikidata-style per-row freeze document (`docs/verification/catalogue-freeze.md`, exhaustive enumeration) cannot scale to hundreds of thousands of rows -- recommend a checksum + aggregate-stats + statistically-sampled-review freeze pattern instead for the IGDB corpus's own DATA-01/DATA-02 equivalent evidence.
- `requests`, `django-allauth`, `dj-rest-auth` are new dependencies this phase will likely need; all three were independently verified legitimate (real PyPI release history) despite the package-legitimacy checker flagging them `SUS` due to an `unknown-downloads` environment gap.
