# Phase 01.1 Plan 04: Plural Simulated Accounts (AUTH-02) Summary

**`bootstrap_demo_accounts` seeds N clearly-labelled `DemoAccountIdentity` rows from an environment-only `DEMO_ACCOUNTS` JSON contract — idempotent create/rotate, advisory-lock serialized, all-or-nothing on any failure, and redacted output that never emits a credential.**

## Accomplishments

- New `DemoAccountIdentity` model: `seed_key` (stable, non-secret identity), deterministic `uuid5` anchor `id` via `demo_identity_anchor_id()`, and a durable public-safe marker (`is_simulated` + `marker` + `display_label`). A DB `CHECK` constraint pins `is_simulated` true.
- New `bootstrap_demo_accounts` management command: parses and fully validates the `DEMO_ACCOUNTS` JSON array before touching the database, runs `validate_password` on every password, then applies all entries inside a single `transaction.atomic()` guarded by `pg_advisory_xact_lock(725_01_15)`. N accounts are created or rotated idempotently; username rotation renames the same row; a duplicate key, duplicate alias, weak password, or alias colliding with an unrelated account aborts with no partial mutation.
- Command output is redacted — `total` / `created` / `rotated` counts plus the list of opaque anchor UUIDs, never a username, password, or hash, on both success and failure paths.
- `bootstrap_demo_account` (singular) rewritten as a thin adapter: builds a one-entry contract from `DEMO_USERNAME` / `DEMO_PASSWORD`, delegates to the shared core, and re-syncs the legacy `DemoAccountAnchor` (still consumed by `seed_demo` and the compose startup chain) inside the same transaction. All 12 pre-existing singular tests stay green.

## Decisions Made

- **Kept `DemoAccountAnchor`, added `DemoAccountIdentity` alongside it.** `seed_demo` and `infra/compose.yaml` both depend on the legacy anchor; replacing it would have been an out-of-scope architectural change. The singular command keeps that row in sync so nothing downstream breaks.
- **One shared advisory-lock key (`725_01_15`) for singular and plural.** They can touch overlapping usernames, so they must serialize against each other, not just against themselves.
- **The seed contract has no built-in default account set.** Like the singular `DEMO_USERNAME`/`DEMO_PASSWORD` rule, `bootstrap_demo_accounts` fails closed when `DEMO_ACCOUNTS` is unset. The contract enforces a minimum of one non-empty, well-formed entry; the acceptance requirement of "at least two independent users" is exercised by the two-account canary contract in the tests.
