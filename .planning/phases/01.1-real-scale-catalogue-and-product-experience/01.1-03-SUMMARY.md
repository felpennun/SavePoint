# Phase 01.1 Plan 03: Catalogue Filter/Sort/Facets Summary

**Validated CAT-02 catalogue query contract — platform/genre/year/rating filters that intersect, a fixed `sort` allowlist with a `canonical_slug` tie-break, bounded 400s for hostile input, and a no-N+1 facet DTO — wired end-to-end into the server-rendered catalogue filter form.**

- **Completed:** 2026-09-05T22:55:21Z
- **Tasks:** 2
- **Files modified:** 10 (+1 created)

## Accomplishments

- `parse_catalogue_query` centralises all CAT-02 parameter validation: the `sort` value is looked up in a fixed `SORT_ORDERS` dict (never interpolated into `order_by`), and unknown sort keys plus non-numeric / out-of-range `year_from` / `year_to` / `min_rating` raise `FilterValidationError`, which the view turns into a bounded HTTP 400 before any ORM access (threat T-01.1-05).
- `search_games` now applies `platform` / `genre` / `year_from` / `year_to` / `min_rating` as intersecting filters on top of the existing tolerant-search result set, keeping `is_dlc=False` throughout, and returns facet options + counts for platforms, genres and the year range in three aggregate queries that do not scale with page size (threat T-01.1-06). Page rows prefetch `releases__platform`, `assets` and `genres` so the card list is query-bounded.
- Every sort key resolves to a total, stable ordering: `title_asc`, `title_desc`, `release_newest` (nulls last), `release_oldest` (nulls last), `rating_desc` (nulls last), each ending in `canonical_slug`; `relevance` is only honoured with a text query and otherwise falls back to `release_newest`.
- `GameWork` gained denormalised `first_release_date` and `total_rating` columns (indexed), plus an index on `original_title` and `GameRelease.release_date`. Migration `0004` backfills `first_release_date` from the releases already loaded so year filtering works against the 312k-row dev corpus immediately; the IGDB importer now persists both scalars going forward.
- `GameCardSerializer` / `GameDetailSerializer` expose `total_rating` and `genres`.
- The catalogue page forwards all filter params to the API and populates the `FilterBar` platform/genre `<select>`s and year-input bounds from `result.facets`; active-filter chips resolve their label from facet names (falling back to the raw slug); pagination and clear-all carry the full query string; the `FilterBar` degrades to search-only when the facet lists are empty (fetch failure). `GameCard`'s `ScorePill` now renders from the real `total_rating`.

## Decisions Made

- **Sort set follows the UI-SPEC, not `must_haves.truths`.** `must_haves.truths` mentions "sort by … popularity", but UI-SPEC Screen Contract 2 (the executable source of truth the prompt points to) and the existing frontend `SORT_KEYS` contain no popularity sort. Implemented the UI-SPEC set exactly. Popularity remains its own endpoint (`/api/library/popularity/`).
- **Unknown platform/genre slug is ignored; unknown sort / out-of-range numeric is a 400.** The plan `<behavior>` enumerates only "unknown sort" and "out-of-range numeric" as 400 cases; UI-SPEC says unknown platform/genre slugs are ignored. Both layers hold: `parse_catalogue_query` accepts any slug string, `_apply_filters` drops it if `Platform`/`Genre` has no such row.
- **Facet counts are computed over the text-scoped set (q + is_dlc), not the fully-filtered set.** This keeps the option lists stable as the user narrows other dimensions and keeps it to three aggregate queries.
