## Accomplishments
- `getPersonalRecommendations(cookieHeader, limit?)` in `apps/web/lib/api.ts` — a typed server-side client for `GET /api/recommendations/genre-taste/`. Forwards the incoming session cookie explicitly (a Server Component's own `fetch()` does not carry request cookies), a `limit` query param, and returns a discriminated union `{ kind: "ok"; data } | { kind: "unauthorized" } | { kind: "error" }` so the page can distinguish "redirect to login" (401/403) from "show a retry state" (transient failure).
- `groupRecommendationsByGenre()` — a pure, directly unit-tested reshaper. The endpoint returns a flat, score-ordered `results[]`; this collects the unique taste genres from each item's `matched_genres`, orders them by taste `weight` (desc, `slug` asc tie-break), caps at 4 shelves x 12 items, and places a work that overlaps several taste genres on each of those shelves. Score order is preserved within a shelf. The insufficient-history / empty shape yields no shelves.
- `apps/web/app/[locale]/recommendations/page.tsx` rewritten to the D-09 contract: auth-gate (`sessionid` cookie -> `/login?next=` redirect; live 401/403 -> same redirect), an `algorithm_id` + `limitation` disclosure block, one `RecommendationShelf` per top taste genre with a per-shelf explainer, per-card genre-overlap evidence, plus explicit insufficient-history and transient-error states. Page chrome (`<h1>` + intro) always renders.
- `RecommendationShelf` now consumes the new `PersonalRecommendationShelf` shape and passes each card a plain-language `evidence` string; `GameCard` gained an optional `evidence` line (additive, no existing caller affected).
- New parallel EN/ES copy: `recommendations.methodHeading`, `recommendations.methodAlgorithm`, `recommendations.shelfEvidence`, `recommendations.cardEvidence`. Dropped the now-unsupported `recommendations.shelfExplainer` CountCopy (removed from `en.ts`, `es.ts`, and `dictionary.ts` together — i18n parity test still green).
- `RecommendationStrip` (REC-02 popularity) left completely untouched — still its own flat "Popular in this demo" `<ol>` on home + game detail, never merged with the personal page.

## Decisions Made
- **`getPersonalRecommendations(cookieHeader, limit?)`, not the plan's literal `(locale, limit?)`.** The genre-taste endpoint is locale-agnostic and the `lib/api.ts` pattern forwards an explicit cookie header (Server Component `fetch()` carries no request cookies). Locale stays a page concern for dictionary lookup. Functionally equivalent to the plan intent: typed, server-side, session-cookie-authenticated call to `GET /api/recommendations/genre-taste/`.
- **Shelves built in the frontend.** Backend returns a flat score-ordered list with per-item `matched_genres`; grouping into "one shelf per top taste genre" (D-UI-4) is presentation and lives in a pure, unit-tested helper.
- **`shelfExplainer` -> `shelfEvidence`.** The old CountCopy needed a per-genre "N games in your collection are {genre}" count the DTO does not carry. Replaced with a plain-language explainer the data supports. Removed from both dictionaries + the interface so parity holds.
- **Signed-out = redirect (+ live 401/403 redirect).** Mirrors `/collection`; a stale `sessionid` cookie still cannot render personal data because the page also redirects on an API 401/403.
- **Backend `limitation` strings are English-only** and surfaced verbatim in the disclosure (the exact contract text is the point). ES page shows the English limitation sentence under a localized heading — a backend-owned limitation, logged below.

## How "authenticated" is determined server-side for the nav-link gate
`apps/web/app/[locale]/layout.tsx` reads `const isAuthenticated = cookieStore.has("sessionid")` (server-side `cookies()`), passes it to `<AppShell isAuthenticated={...}>`. `AppShell.buildNavItems(dict, locale, isAuthenticated)` pushes the `/[locale]/recommendations` (and `/collection`) nav items **only** when `isAuthenticated` is true, so signed-out navigation contains no personal link (threat T-01.1-10). This gate predates this plan (01.1-06); this plan relies on it and additionally hard-gates the page itself: no `sessionid` cookie -> `redirect` to `/[locale]/login?next=/[locale]/recommendations`, and a live `401/403` from the `IsAuthenticated` endpoint triggers the same redirect — so a stale or forged `sessionid` cookie cannot render any personal data.
