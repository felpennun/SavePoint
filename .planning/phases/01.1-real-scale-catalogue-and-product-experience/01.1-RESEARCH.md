## Summary

This phase turns Phase 1's 150-game curated demo into a real-scale product. Five things need new engineering the codebase does not yet have at all: (1) an IGDB-based bulk importer that must survive being interrupted mid-run over what could be a multi-day pull, (2) a `Genre` entity that does not exist anywhere in the current schema (`catalogue/models.py` has `GameWork`, `Platform`, `GameRelease`, `Edition`, `GameAlias`, `RelatedContent`, `SourceRecord`, `AssetAttribution` -- no genre, no tag, no franchise), (3) a self-service registration endpoint layered onto the existing hand-rolled, non-`allauth` accounts app, (4) real filter/sort UI and API query support (today's `GameListView`/`search_games` only takes `q`/`page`), and (5) a new recommendations endpoint that must stay visibly simpler than Phase 6's real content-based recommender.

The single most consequential technical finding is that **the existing Wikidata import pattern (`import_catalogue.py`) does not scale to IGDB's hundreds of thousands of rows as written**: it loads the entire snapshot into memory and processes every row inside one `transaction.atomic()` block holding one PostgreSQL advisory lock for the whole run. At Wikidata's 150 rows this is fine; at IGDB's ~230K-430K rows it means a single bad record near the end discards hours of already-completed work, and the advisory lock would be held open for however long the whole run takes. The import needs batched transactions with a resumable cursor, not scaled-up copy of the existing single-transaction pattern -- but it should keep the existing pattern's idempotent `update_or_create` keying on `SourceRecord(source, source_id)`, which already makes replaying any given page safe.

The second major finding is a direct conflict inside the project's own locked requirements: `01.1-CONTEXT.md`'s open question asks whether "real login system" should include self-service registration, but `.planning/REQUIREMENTS.md`'s Out-of-Scope table already states "Open production registration in v1 | Initial release is a controlled academic demonstration" is out of scope for v1, and `AUTH-03` ("Visitor can register an unrestricted production account") is explicitly a v2 requirement. Any self-service registration this phase adds must be something other than what `AUTH-03` describes, or the phase would silently pull a v2 requirement into v1. See Open Questions.

Third, the IGDB rate-limit/quota numbers in this research are **triangulated from multiple independent secondary sources, not read directly from `api-docs.igdb.com`** -- that page returned `403 Forbidden` to this session's fetch tool (likely bot/Cloudflare protection) on every attempt, including via the Wayback Machine. All numeric IGDB claims below are tagged accordingly and should be independently confirmed by the executor against a real, authenticated API call (trivial to do -- register a Twitch app and probe the API directly) before the import architecture is finalized.

**Primary recommendation:** Build the IGDB importer as a two-phase pipeline (fetch-to-local-snapshot, then batched-transaction load) with a resumable cursor keyed on IGDB's numeric `id` (never raw offset, per a documented IGDB community report that deletions shift offset-based pagination), replace the single per-import freeze document with a statistical-sample freeze (full snapshot checksum + aggregate coverage stats + a sampled manual review, not an enumerated per-row/per-asset table), add a minimal `Genre` model now (deferring the rest of `CAT-05`'s franchise/developer/publisher/mode/tag entities to Phase 4), extend the existing hand-rolled `accounts` app with a `RegisterView` mirroring `LoginView` rather than adopting `django-allauth`, and keep the new recommendations page a stateless, request-time genre-frequency heuristic mirroring `library/popularity.py`'s pattern rather than a trained/persisted model.

### Pattern 1: Resumable cursor-based pagination (not offset-based)

**What:** Page IGDB results using `where id > <last_seen_id>; sort id asc; limit 500;` and persist `<last_seen_id>` to a checkpoint file/row after every successfully-imported page, instead of an offset counter.
**When to use:** Any multi-page pull expected to run long enough to be interrupted (network blip, rate-limit backoff, process restart) -- explicitly the case here per the author's own multi-day framing.
**Why not offset:** A Twitch Developer Forums thread surfaced during this research reports that IGDB's dataset changes underneath long-running pulls (records get deleted), and a moderator's own warning is that deletions "throw off your restart point" for offset-based pagination -- resuming from a stale offset silently skips or duplicates rows. `id`-based cursoring is monotonic and immune to this. `[CITED: discuss.dev.twitch.com/t/igdb-store-all-games-in-local-database/47241 -- read via WebFetch this session, moderator reply paraphrased above, not a verbatim quote captured]`
**Example (Apicalypse, illustrative -- exact field names should be confirmed against a live IGDB call before implementation, see flag below):**
```
fields id,name,slug,genres.name,platforms.name,cover.image_id,first_release_date,total_rating;
where id > 118532;
sort id asc;
limit 500;
```

### Pattern 2: Batched-transaction import with per-batch advisory lock, not one giant transaction

**What:** Split the load into fixed-size batches (e.g. 1,000-5,000 rows), each wrapped in its own `transaction.atomic()` + `pg_advisory_xact_lock`, with a persisted "last successfully imported batch" checkpoint.
**When to use:** Any import expected to process far more rows than the existing `import_catalogue.py`'s 150-row Wikidata case, where the current single-transaction-for-the-whole-run pattern would hold locks for hours and discard all progress on a late failure.
**Source:** Directly adapted from reading `apps/api/catalogue/management/commands/import_catalogue.py` this session (`[VERIFIED: apps/api/catalogue/management/commands/import_catalogue.py:107-109]` -- the existing single `with transaction.atomic(): ... cursor.execute("SELECT pg_advisory_xact_lock(%s)", [IMPORT_LOCK_KEY])` wraps the entire per-game loop, not per-batch).
**Example (illustrative shape, following the existing file's own idiom):**
```python
CHECKPOINT_KEY = "igdb_import_last_batch"

for batch in chunked(games, size=2000):
    with transaction.atomic():
        with connection.cursor() as cursor:
            cursor.execute("SELECT pg_advisory_xact_lock(%s)", [IMPORT_LOCK_KEY])
        for game in batch:
            # same update_or_create-on-SourceRecord(source, source_id) idiom
            ...
        ImportCheckpoint.objects.update_or_create(
            key=CHECKPOINT_KEY, defaults={"last_igdb_id": batch[-1]["id"]}
        )
```

**What:** Extend `apps/web/app/[locale]/catalogue/page.tsx`'s existing `<form action=... method="get">` pattern with `<select>` controls for platform/genre/sort and a year-range or rating-range input, all read from `searchParams` server-side exactly like `q`/`page` are today.
**Why:** `[VERIFIED: apps/web/app/[locale]/catalogue/page.tsx -- full file read this session]` -- the page is an `async` Server Component with zero client-side JS for search today; a filter bar built the same way keeps it URL-shareable/bookmarkable (a Goodreads/OpenCritic pattern observed directly, see State of the Art) and avoids introducing client-side state management this phase does not otherwise need.

### Anti-Patterns to Avoid

- **One giant transaction for the whole IGDB import:** see Pattern 2. The existing Wikidata importer's shape is correct at 150 rows and actively dangerous at 230K+ rows.
- **Offset-based resumable pagination:** see Pattern 1.
- **Treating IGDB cover licensing like Wikidata Commons cover licensing:** the existing `AssetAttribution` model (`creator`, `licence`, `licence_url`, `reviewed_at`, `display_allowed`) was designed for per-file Creative Commons review of 19 hand-checked Wikimedia Commons images (`docs/verification/catalogue-freeze.md`, `[VERIFIED: docs/verification/catalogue-freeze.md:41-74]`, 17 `candidate`/2 `placeholder` out of 19 candidates, each with an individually verified author/licence/licence-URL). That per-file manual-review model does not scale to (and is not the right legal model for) hundreds of thousands of IGDB-hosted covers governed by one blanket Twitch Developer Services Agreement, not per-image CC licences. Populate `AssetAttribution.licence`/`licence_url` with the IGDB/Twitch terms reference for every IGDB-sourced cover rather than attempting individual per-cover legal review -- and record that modeling choice explicitly in the DATA-04 ADR.
- **N+1 IGDB queries per game for genres/cover/platforms:** Apicalypse supports dot-path field expansion (`genres.name`, `cover.image_id`, `platforms.name`) in a single request; querying genres or cover data as separate follow-up requests per game would multiply request counts against the rate limit for no reason.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: Trusting a stale "50,000 requests/month" IGDB quota figure

**What goes wrong:** Designing the import pacing (e.g. "spread 300K requests over N days to stay under a monthly cap") around a monthly request quota that no longer applies to the current API version.
**Why it happens:** IGDB had a genuine 50K-requests/month cap on an older pricing tier (pre-"v4"/pre-Twitch-integration API, hosted on RapidAPI) that multiple sources this session describe as having been **removed** when IGDB moved under Twitch and introduced the current 4-requests/second + up-to-8-concurrent rate limit with **no monthly cap** mentioned by any source found this session. `[CITED: WebSearch synthesis of igdb-api-v4-is-coming Medium post + Twitch Developer Forums thread "IGDB, authentication and tokens" -- not independently read verbatim; see the explicit low-confidence flag below]`
**How to avoid:** Before finalizing the import's pacing/checkpointing design, have a human (or the executor with real credentials) make one authenticated test call against `https://api.igdb.com/v4/games/count` and read the actual response headers/any documented quota directly -- this is a five-minute positive-falsification check that resolves the open question far more reliably than further web search.
**Warning signs:** Any plan step that says "throttle to N requests/day to stay under the monthly cap" without a dated, primary-source citation for that cap's current existence.

### Pitfall 2: The freeze-document pattern doesn't scale to per-row manual review

**What goes wrong:** Trying to reuse `docs/verification/catalogue-freeze.md`'s exact shape (an enumerated, individually-reviewed table of every asset's licence/creator/URL, `[VERIFIED: docs/verification/catalogue-freeze.md:41-74]`) at IGDB scale -- this was hand-reviewable at 19 candidate images; it is not reviewable by a human at hundreds of thousands.
**Why it happens:** The Wikidata freeze document is the only precedent in the codebase, and its shape (full enumeration) was correct at its own scale.
**How to avoid:** Design the IGDB freeze document around: (1) the same snapshot-checksum mechanism (`sha256` of the canonical raw JSON, already proven in `import_catalogue.py`'s `_check_checksum`), (2) aggregate coverage statistics (counts by platform/genre/era, mirroring the existing freeze doc's own coverage table), and (3) a statistically-sampled manual spot-check (e.g., N=200-500 random records reviewed for correctness) instead of an exhaustive per-row table -- explicitly documenting that the legal basis for cover images is the blanket IGDB/Twitch API terms, not per-image review, per Anti-Pattern 3 above.
**Warning signs:** A plan task that says "enumerate every imported game/asset in the freeze document" at IGDB's scale.

### Pitfall 3: One giant import transaction for hundreds of thousands of rows

**What goes wrong:** Copying `import_catalogue.py`'s single `with transaction.atomic(): ... for game in games: ...` shape directly onto the IGDB dataset. A late failure (one bad record near row 400,000) rolls back the entire run; the single `pg_advisory_xact_lock` is held for the whole run's duration, which could be hours, blocking any other invocation (including a legitimate resume attempt after a crash, since the lock only releases on transaction end).
**Why it happens:** It is the only precedent in the codebase, and it is correct at 150 rows.
**How to avoid:** Batch the transaction (Pattern 2 above); persist a resumable checkpoint outside any single transaction's rollback scope.
**Warning signs:** Any IGDB import plan step whose `<verify>` only checks the *final* row count with no intermediate progress/checkpoint evidence.

### Pitfall 4: `AUTH-03`'s v2 boundary vs. this phase's "self-service registration" open question

**What goes wrong:** Implementing open, unrestricted self-service registration this phase, which would silently deliver `AUTH-03` ("Visitor can register an unrestricted production account") a full milestone early, directly contradicting `REQUIREMENTS.md`'s own Out-of-Scope table entry: `"Open production registration in v1 | Initial release is a controlled academic demonstration."` `[VERIFIED: .planning/REQUIREMENTS.md:138 (AUTH-03 listed under v2 Requirements), :151 (Out of Scope table row "Open production registration in v1")]`
**Why it happens:** `01.1-CONTEXT.md`'s own open question ("preloaded accounts only, or also self-service registration?") does not cross-reference this existing scope boundary -- it was captured from the author's words in isolation.
**How to avoid:** Surface this conflict explicitly at `/gsd-discuss-phase` or planning time rather than resolving it silently either direction. A middle path exists and should be proposed to the author: self-service registration that is still "controlled" in some way (e.g., requires an access code distributed to the thesis tribunal/reviewers, or is rate-limited/admin-approved) would add real self-service registration capability without literally delivering `AUTH-03`'s "unrestricted production account." See Open Questions.
**Warning signs:** A plan step titled simply "add public registration" with no reference to this boundary.

### Pitfall 5: Missing `next.config.ts` remote-image allowlist for IGDB's CDN

**What goes wrong:** IGDB-hosted cover URLs (`images.igdb.com`) rendered via `next/image` will be rejected at runtime unless the domain is added to `images.remotePatterns` -- `[VERIFIED: apps/web/next.config.ts -- full file read this session, no `images` key present at all today]`.
**Why it happens:** Phase 1 never needed this because Wikidata/Commons cover URLs, if rendered at all, would hit the same gap -- this simply hasn't been exercised yet.
**How to avoid:** Add the chosen image host(s) to `next.config.ts`'s `images.remotePatterns` as part of the frontend work, and decide hotlink-vs-mirror (see Alternatives Considered) before writing that config, since the two approaches need different `remotePatterns`/storage-serving setups.

## Open Questions

1. **Does IGDB still enforce a monthly request quota, and if so what is it?**
   - What we know: 4 requests/second + up to 8 concurrent is corroborated across multiple independent secondary sources; a 50,000/month figure existed on a now-superseded API tier.
   - What's unclear: Whether the "no monthly cap" conclusion is actually current, since it rests entirely on secondary-source triangulation (the primary docs page returned 403 to every fetch attempt this session).
   - Recommendation: Executor makes one real authenticated API call (`/games/count` or similar) at the start of implementation and reads response headers/any documented quota directly before finalizing import pacing.

2. **Self-service registration: how does it coexist with the "no open production registration in v1" scope boundary (Pitfall 4)?**
   - What we know: `01.1-CONTEXT.md` leaves this open; `REQUIREMENTS.md` already has an opinion (v1 excludes it, `AUTH-03` is v2).
   - What's unclear: Whether the author, on discovering this conflict, wants (a) preloaded-accounts-only for this phase with self-service deferred to when `AUTH-03` is actually scheduled, (b) a gated/controlled self-service registration that isn't literally `AUTH-03`, or (c) an explicit re-scope of `AUTH-03`/the Out-of-Scope table.
   - Recommendation: Raise explicitly at discuss-phase/planning rather than picking one silently.

3. **Hotlink IGDB's cover CDN or mirror covers locally?**
   - What we know: Both are technically viable; hotlinking is lower storage cost and matches common IGDB-consumer practice; mirroring matches the existing `AssetAttribution.local_path` field's apparent original intent (currently unused/empty even for Wikidata).
   - What's unclear: Whether IGDB's terms have any distinction between the two for a non-commercial academic project, and whether the free-tier deployment topology (`Vercel Hobby + Render Free + Neon Free`) can absorb mirrored-image storage/bandwidth at scale even if terms permit it.
   - Recommendation: Resolve as part of the DATA-04 ADR alongside the primary IGDB-vs-RAWG-vs-Wikidata comparison, not as a separate decision later.

4. **Exact catalogue scale target: literally all of IGDB, or a large bounded subset?**
   - What we know: Author's stated ambition is "the entire IGDB catalogue, hundreds of thousands of titles"; `01.1-CONTEXT.md`'s own open-questions section already flags this as unresolved ("not necessarily every single IGDB entry").
   - What's unclear: Whether a bounding filter (e.g. exclude entries IGDB itself categorizes as bundles/ports/forks/versions -- Backloggd's category filter list surfaced this same category-noise problem) should be applied, given `RelatedContent`'s existing DLC/expansion model and `is_dlc` flag already establish precedent for excluding non-primary entries from catalogue results.
   - Recommendation: Default to importing everything IGDB returns for the `games` category filtered to exclude obvious non-primary categories (ports/forks/bundles/episodes, mapped onto the existing `is_dlc`/`RelatedContent` model rather than a new field), confirm the resulting count against the author's "hundreds of thousands" expectation, and treat this as a tunable import-time filter rather than a schema decision.
